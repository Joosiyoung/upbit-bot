# 트레이딩 봇 구축 플레이북

새 트레이딩 봇 프로젝트를 시작할 때 그대로 적용할 수 있는 설계·검증 방법론.
Fable(업비트 봇) 프로젝트에서 정립했으며, 거래소·자산·언어가 달라져도 구조는 동일하게 적용된다.
이 문서 하나를 새 프로젝트 루트에 복사하고 따라가면 된다.

---

## 1. 핵심 설계 원칙 (타협 불가)

1. **동일 코드 3모드 원칙**: 전략·리스크·실행 코드는 백테스트/페이퍼/실거래에서
   단 한 줄도 바뀌지 않아야 한다. 바뀌는 것은 "캔들 공급원"과 "브로커 구현체"뿐.
   → 백테스트로 검증한 것이 실전에서 그대로 도는 것을 보장하는 유일한 방법.
2. **책임 분리 파이프라인**: 전략은 의도(Signal)만, 리스크는 수량과 차단만,
   브로커는 체결만 담당한다. 전략 코드에 잔고·수수료·한도 로직이 섞이면 안 된다.
3. **비용 없는 백테스트 금지**: 수수료+슬리피지 미반영 결과는 폐기 대상.
4. **실거래는 마지막**: 백테스트 → 페이퍼(실시간 모의) → 소액 실거래 순서를 건너뛰지 않는다.

## 2. 아키텍처

### 데이터 흐름 (모든 모드 공통)

```
시세 공급원                     ┌─ 백테스트: 과거 캔들 재생
(Candle 이벤트)  ◄──────────────┤─ 페이퍼:   WebSocket 틱 → 캔들 집계
      │                        └─ 실거래:   페이퍼와 동일 공급원
      ▼
Strategy.on_candle(candle, position) → [Signal(side, price, strength, reason)]
      ▼
RiskManager.evaluate(signal) → Order | None    # 사이징 + 차단 게이트
      ▼
Executor.execute(order) → Fill | None          # 재시도·로깅·알림 훅
      ▼
Broker (추상 인터페이스)        ┌─ PaperBroker: 가상 잔고 + 수수료·슬리피지 (백테스트·페이퍼 공용)
                               └─ RealBroker:  거래소 API (마지막에 구현)
      ▼
Storage: 체결 로그 + 자본 곡선 + 상태 스냅샷 (재시작 복구)
```

### 디렉토리 구조

```
project/

│   ├── models.py            # Candle, Signal, Order, Fill, Position, TradeRecord
│   ├── settings.py          # 설정 로더

│   ├── data/                # collector.py(REST 과거 + WS 실시간·집계) + storage.py
│   ├── strategy/            # base.py(인터페이스) + 전략 구현체들
│   ├── risk/manager.py
│   ├── execution/executor.py
│   ├── backtest/            # engine.py + metrics.py

└── tests/
```

### 핵심 인터페이스 (언어 무관 시그니처)

```
Strategy:
    on_candle(candle, position) -> list[Signal]   # 상태는 내부 보관, 수량 결정 금지
    warmup(candles)                                # 과거 데이터로 지표 초기화 (신호 발생 없음)
    seed_today(candle)                             # 장중 시작 시 당일 진행 캔들 주입 (일 단위 전략)

Signal:  market, side(BUY/SELL), price(기대 체결가), strength(0~1, 비중 조절), reason(문자열 필수!)
         → reason은 나중에 "청산 사유별 손익 분해"의 키가 된다. 반드시 기록.

RiskManager:
    update_equity(timestamp, equity)   # 날짜 롤오버 감지 → 일일 한도 리셋, 킬스위치 검사
    evaluate(signal) -> Order | None   # 매도는 항상 통과, 매수만 차단

Broker:
    buy(order) / sell(order) -> Fill | None
    get_position(market) -> Position
    equity(prices) -> float
    snapshot() / restore(snap)         # 페이퍼·실거래 재시작 복구용
```

## 3. 리스크 관리 규칙 (기본값)

| 규칙 | 기본값 | 동작 |
|---|---|---|
| 포지션 사이징 | 자본 × 30% × strength | strength = min(1, 목표변동성/전일변동폭) |
| 일일 손실 한도 | -3% | 당일 신규 매수 차단, 다음 날 자동 리셋 |
| 킬스위치 | 최고 자본 대비 -15% | 전량 청산 후 **영구 정지** (수동 해제만 가능) |
| 최소 주문 금액 | 거래소 규정 | 미달 주문은 브로커가 거부 |
| 매도 우선 | 항상 | 차단 상태에서도 청산은 허용 |

운영 리스크: API 레이트리밋 준수, WebSocket 지수 백오프 재연결, 모든 상태(잔고·포지션·리스크)를
매 이벤트마다 영속화 → 프로세스 강제 종료 후 재시작해도 이어서 동작해야 한다 (이것도 테스트 대상).

## 4. 전략 우선순위와 함정

1. **규칙 기반부터** (변동성 돌파, MA 크로스 등): 구현·검증이 명확, 인프라 검증을 겸함.
   - 변동성 돌파: `목표가 = 당일시가 + k×전일변동폭`, k≈0.5. 개선: MA 상승 필터, 변동성 타게팅.
   - 지표(RSI·MACD)는 단독 신호가 아니라 필터로만.
2. **ML은 백테스트 인프라 완성 후**: 방향 분류 > 가격 회귀. walk-forward 검증 필수.
   룩어헤드(미래 데이터 누출)와 과적합이 2대 함정.
3. **마켓메이킹/차익거래는 후순위**: 단일 거래소 수수료 대비 스프레드, 복수 거래소 규제·송금 이슈.

타임프레임 이중 지원: 일 단위 전략은 (a) 일봉 모드 — 한 캔들 안에서 돌파매수→종가청산 근사(백테스트),
(b) 분봉 모드 — 날짜 경계에서 청산·목표가 재계산(실시간). 같은 클래스에서 둘 다 지원하게 설계.

## 5. 검증 체크리스트 (순서대로)

- [ ] **단위 테스트**: 전략 신호(알려진 캔들 → 기대 신호), 브로커 수수료·슬리피지 계산,
      리스크 한도·킬스위치, 캔들 집계기, 스냅샷 복구
- [ ] **합성 데이터 E2E**: 손으로 계산 가능한 캔들 몇 개로 엔진 전체 파이프라인 검증
- [ ] **비용 민감도**: `--fee-rate 0` 비교 실행. 수익 차이가 없으면 비용 모델이 죽어 있는 것
- [ ] **과최적화 검증**: 파라미터 스윕을 in-sample/out-of-sample로 분리 (`--sweep --split 날짜`).
      in-sample 최고가 out-of-sample에서도 상위권인지 확인
- [ ] **평가 지표**: 누적수익률이 아니라 MDD·샤프·손익비(PF)·거래당 기대값 중심
- [ ] **청산 사유별 손익 분해**: 손실이 어느 경로(손절/시간청산/신호)에서 새는지 항상 확인
      → 이것이 "브래킷 조정 문제인지 진입 품질 문제인지"를 가르는 진단
- [ ] **페이퍼 트레이딩**: 수일 이상 실시간 구동. 중간에 프로세스 kill → 재시작 복구 확인
- [ ] **벤치마크 비교**: 과거 전략/봇의 실측 데이터가 있으면 동일 기간·동일 회계(수수료 반영)로
      나란히 비교. 시장 국면 효과와 전략 효과를 분리해서 해석

## 6. 실측으로 확인된 교훈 (Fable 프로젝트, 2026-07)

- **백테스트-실전 괴리는 실재한다**: 이전 봇(점수제)은 백테스트 +0.15%/거래였지만
  실시간 시뮬 271건에서 **-0.45%/거래** (수수료 반영). 페이퍼 검증 단계는 생략 불가.
- **청산 분해가 원인을 밝힌다**: 위 손실의 주범은 청산의 49%를 차지한 손절(평균 -3.98%)이
  익절(+6.03%)을 압도한 구조. TP/SL 브래킷 조정(6/4→5/3)으로는 해결 안 됨 = 진입 품질 문제.
- **시장 국면과 함께 해석**: 같은 약세 구간에서 변동성 돌파도 -0.37%/거래.
  전략이 나쁜 게 아니라 장이 나쁠 수 있다 — 기간 수익률만 보고 전략을 버리지 말 것.
- **승률 40%대 + 손실 중앙값이 평균보다 나쁘면**: 소수 큰 승리에 의존하는 구조.
  거래 수가 충분히 쌓이기 전에는 평균을 신뢰하지 말 것.

## 7. 구현 순서 (마일스톤)

| Phase | 내용 | 완료 기준 |
|---|---|---|
| 1 | 스캐폴드 + 모델 + 데이터 수집·저장 | 과거 캔들이 Parquet으로 쌓인다 |
| 2 | 백테스트 엔진 + 1호 전략 + 지표 | 비용 민감도·스윕 검증 통과 |
| 3 | 페이퍼 트레이딩 (1차 마일스톤) | 수일 구동 + 강제종료 복구 확인 |
| 4 | ML 전략 / 전략 추가 | walk-forward로 기존 전략 대비 우위 |
| 5 | 소액 실거래 | 페이퍼와 실거래 성과 괴리 측정 |

각 Phase는 이전 Phase의 완료 기준을 통과하기 전에 시작하지 않는다.
